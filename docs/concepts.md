# Concepts

The model envstore exposes, in order from broadest to narrowest. If you
already understand "workspace > project > environment > version" from other
secrets vendors, the surprises here are: **identities**, **service tokens**,
and the **trust cache**.

## Workspace

A billing and access boundary. Two flavors:

- **Personal** — every account gets one automatically. Slug is your username;
  in URLs and the CLI it appears as the sentinel `me` (for example,
  `envstore.xyz/me/api-keys`). Unlimited projects, but only you can decrypt.
- **Team** — invite other members. Every push encrypts to every member's
  recipient. Billing is **per workspace**, flat, regardless of member count.

A workspace owns: projects, members, service tokens, audit log entries, and a
soft-delete retention setting.

## Project

A logical secret namespace inside a workspace. Typically one project per
deployable service: `api`, `worker`, `web`, `marketing-site`.

In monorepos you'll usually have several projects under one workspace, all
described in a single `envstore.json` (the multi-config form — see
[envstore.json](#envstorejson) below).

## Environment

A named slot within a project: `development`, `staging`, `production`,
`preview-42`, whatever your deploy pipeline uses. Environments are created
on first push (you don't pre-declare them). Each environment carries a
sequence of immutable versions and a pointer to the **current** one.

Environment slugs auto-detect from filenames where possible
(`.env.production` → `production`). Bare `.env` and `.env.local` are treated
as "no qualifier" — the CLI prompts you for the slug the first time.

## Version

Every successful push creates a new version row: a monotonically-incrementing
integer per environment, an R2 object key for the ciphertext, the size and
sha-256 of that ciphertext, the recipients hash it was encrypted to, and an
optional comment.

The environment's `currentVersion` pointer is what `envstore pull` returns.
It moves forward on every push, and can be moved to any retained prior
version with [`envstore rollback`](commands.md#envstore-rollback) — the
rollback is just a pointer flip, no re-encryption. List the history with
[`envstore versions`](commands.md#envstore-versions); pull a specific
historical version with `envstore pull <env> --version <n>`.

Each workspace has a `versionHistoryLimit` (default 50, configurable
5–500 in workspace settings). After every push, versions older than the cap
are pruned in the same transaction; the current pointer is always preserved
even if it falls outside the cap.

## Recipient

A public key the CLI encrypts to. Two kinds:

- **age X25519** (`age1...`) — the default. Generated by
  `envstore identity init` on your machine.
- **SSH Ed25519** (`ssh-ed25519 ...`) — registered if you already use an
  SSH key for git; encryption uses the ssh-to-age conversion supported by
  the age format.

A workspace push fetches the union of every member's recipients plus every
active service token's recipient, deduplicates, and encrypts to all of them.
That's why adding a teammate doesn't break old versions for current members,
and why removing a teammate requires a [`rekey`](commands.md#envstore-rekey)
to re-encrypt to the new (smaller) set.

## Identity

The **local** half of a recipient — the secret key that decrypts. envstore
generates this on your machine and never receives it. By default it lives
in macOS Keychain (with a file fallback at
`~/.config/envstore/identity.age` on platforms without one).

Your identity is your only path to past secrets. Lose every copy of it and
the data is gone. The recommended hygiene:

1. After `envstore identity init`, immediately
   `envstore identity export --clipboard` and paste into a password manager
   (1Password, Apple Passwords, Bitwarden, whatever).
2. On any second machine, `envstore identity import` from that backup —
   same identity, no rekey needed.

You can register more than one recipient (one per machine), in which case
pushes encrypt to all of them. That gives you per-device revocation: drop a
recipient from your account, then `rekey` to evict the old key from future
versions.

## Service token

A non-human credential for CI/CD. Created by `envstore token create`, which
does three things in one shot:

1. Generates an X25519 keypair on your laptop. The **private** key never
   touches the server.
2. Registers the **public** half with the workspace as a recipient with
   `recipientKind = AGE_X25519` (so future pushes encrypt to it).
3. Prints a bearer token (`eswtok_…`) for HTTP auth.

The CI provider gets two secrets:

- `ENVSTORE_TOKEN` — the bearer.
- `ENVSTORE_IDENTITY` — the matching secret key.

Tokens can be scoped to specific projects (`--projects api,worker`) and
optionally expire (`--expires 90`). They cannot mint other tokens, change
membership, or alter ACLs — the blast radius of a leak is the workspace's
current ciphertext.

## Trust cache

A local file (`~/.config/envstore/trust.json`, mode 0600) where the CLI
remembers the recipient set it has previously encrypted to for each
(apiUrl, workspace, project) tuple.

On every push, the CLI compares the server's response to its cache:

- **Unchanged** — proceed silently.
- **New entries appeared** — pause, show the new recipients, ask before
  encrypting. In CI you can pass `--trust-new` to auto-accept.
- **Trust-on-first-use** — the very first push from a workstation accepts
  whatever the server returns. After that, the diff check kicks in.

This is envstore's defense against an actively-compromised server quietly
injecting an attacker's key into your recipient set to read future pushes.
Inspect or reset the cache with [`envstore trust`](commands.md#envstore-trust).

## envstore.json

Every project root has one. Two shapes:

**Flat** (single project):

```json
{
  "$schema": "https://envstore.xyz/schema/envstore.json",
  "workspace": "acme",
  "project": "api",
  "defaultEnv": "development"
}
```

**Multi** (monorepo — one entry per `.env` file in the tree):

```json
{
  "$schema": "https://envstore.xyz/schema/envstore.json",
  "workspace": "acme",
  "files": [
    { "path": "apps/web/.env.local", "project": "web", "environment": "development" },
    { "path": "apps/api/.env", "project": "api", "environment": "development" },
    { "path": "apps/api/.env.production", "project": "api", "environment": "production" }
  ]
}
```

`envstore init` walks the tree on first setup; `envstore sync` reconciles
the file later when you add or remove `.env` files.

Commit `envstore.json` to your repo — it contains zero secrets and lets
teammates run `envstore link` (or just `envstore pull`) without a separate
config step.

## How they relate

```
Workspace (acme)
├── Members → recipients (age1...) — added when each member runs `identity init`
├── Service tokens → recipients (age1...) — added when minted
└── Projects
    ├── api
    │   ├── Environment: development
    │   │   ├── Version 1 (r2://…/v1, sha256=…, recipientsHash=…)
    │   │   ├── Version 2 …
    │   │   └── currentVersion → 2
    │   └── Environment: production
    │       └── …
    └── worker
        └── …
```

A push of `apps/api/.env.production` writes a new version row to
`acme/api/production` with ciphertext encrypted to the union of all
workspace recipients. A pull reverses the flow. A rekey re-encrypts past
versions to today's recipient set.
